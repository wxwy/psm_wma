# R09-B2 P5 v0.5 static tools implementation review

- Request: `36a3d0588c556a580e67c5ed7fd20fe79688b763`
- Reviewed root: `2534afcef4b269dd47e9d083044dda708359dc21`
- Reviewed Gitlink/submodule: `21d064f2b7c7aeeb67cfee50ac8d6722a944eddb`
- Verdict: **REQUEST_CHANGES**

## Findings

### HIGH — three-root isolation is not enforced

`tools/g0/export_r09_b2_p5_resolved_config.py:170-210`
`tools/g0/verify_r09_b2_p5_full_config_diff.py:145-170`
`tools/g0/test_r09_b2_p5_full_config_diff.py:18-42`

The v0.4/v0.5 contract requires `production_root`, `evidence_root`, and `exporter_root` to be canonical, independently validated, and non-overlapping. The implementation accepts the three roots separately but never rejects overlap or symlink-equivalent roots. `verify_pair()` validates only `evidence_root` and `exporter_root` independently. The positive CPU fixture actually calls `verify_pair(..., root, root)`, using the same checkout as both evidence and exporter, which demonstrates that the core three-root separation is not enforced.

Required:
- canonicalize all three roots before use;
- require pairwise distinct resolved roots and reject ancestor/descendant overlap where it would defeat isolation;
- reject symlink aliases resolving to an already-used root;
- add a permanent negative for `evidence_root == exporter_root` and for symlink-equivalent roots.

### HIGH — production_root is revision-bound but not tracked-clean

`tools/g0/export_r09_b2_p5_resolved_config.py:120-145`

`validate_production_root()` verifies the absolute D005 root, root HEAD, Gitlink, and submodule HEAD, but it never checks tracked cleanliness of either the root repository or `cosmos-framework`. A dirty checkout at the frozen `ddb4e0e`/`21d064f` revisions can therefore alter the Python config or production compose source while still satisfying the recorded source revision and absolute path.

This violates v0.4's explicit `tracked-clean` production-root contract and can make the exported resolved config differ from the frozen production source while provenance still reports `ddb4e0e`.

Required:
- require `git diff --quiet HEAD --` for `production_root` and its submodule before child request construction;
- add a CPU/git fixture proving a tracked modification causes FAIL before compose.

Also complete the v0.5 containment check: the implementation checks D005 `cwd`, `PYTHONPATH`, and `PSM_R09_B2_STREAM_MANIFEST_ROOT`, but not the frozen `inputs.external_assets.stream_manifest.path/realpath` required by the v0.5 design.

### HIGH — evidence_root does not bind the closed P4 pair to frozen committed evidence identities

`tools/g0/export_r09_b2_p5_resolved_config.py:155-165`
`tools/g0/verify_r09_b2_p5_full_config_diff.py:88-100, 145-170`

The verifier loads whichever P4 recurrent/TTT JSON files currently exist in `evidence_root`, and computes the current `verification.json` SHA dynamically. There is no frozen expected SHA for the closed recurrent record, TTT record, or P4 verification artifact, nor an independent check that the P4 verification artifact is the committed closed PASS evidence.

`provenance.inputs.p4_record_sha256` is also not the committed record-file SHA: it is recomputed as `sha256_json(record without d005_sha256)`, i.e. the record's internal digest payload. A clean evidence checkout containing a self-consistently modified P4 record/verification can therefore become the new verifier truth.

Required:
- bind the evidence root to the already-closed P4 record file SHA256 values and P4 verification file SHA256 value (or an equivalently immutable closure manifest);
- verify the P4 verification schema/status and frozen identity, not merely hash the current file;
- record the actual committed P4 record-file SHA separately from `d005_sha256`/record-digest semantics;
- require evidence_root tracked-clean as specified by v0.4;
- add a regression where both envelopes and a clean forged evidence checkout are self-consistent but differ from the frozen P4 evidence; verifier must FAIL.

### HIGH — exact nested envelope schema is still not fail-closed

`tools/g0/verify_r09_b2_p5_full_config_diff.py:108-145`

The verifier enforces the top-level envelope key set, the top-level provenance key set, and the command key set. It does not enforce exact key sets for `provenance.inputs`, `effective_launch`, `environment`, or `p1_p3_d005_bindings`. Common extra fields inserted identically into both envelopes are invisible to pair diffing and are not rejected by `_bound()`.

This contradicts the v0.4 requirement that every nested envelope section have an exact field set.

Required:
- enforce exact nested schemas for every verifier-owned envelope object before any value comparison;
- add a negative where the same unknown field is inserted on both sides under each verifier-owned nested object and require FAIL.

## What is correctly improved

- D005 absolute production root is derived from both records and relocation is rejected.
- Worktree-bound `cwd`, `PYTHONPATH`, and stream-manifest environment root are checked for containment.
- Exporter provenance is independently recomputed from `exporter_root`; caller-provided exporter revision/SHA cannot pass unless it matches the tracked exporter checkout.
- Child module-level root `tools.g0` dependency has been removed; the subprocess smoke reaches the pre-compose guard under the frozen D005 cwd/environment without invoking compose.
- Unique attempt staging plus final rename prevents a failed attempt from occupying the canonical output path.
- Resolved `local_history_backend` and full optimizer selector list are checked per backend before diff allowlisting.

No static export, `load_experiment_from_toml`, CUDA/GPU, torchrun, model construction, training, evaluation, inference, P5 closure, or B2-T is authorized by this review.
