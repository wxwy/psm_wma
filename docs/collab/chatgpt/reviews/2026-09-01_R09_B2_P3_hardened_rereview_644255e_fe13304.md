## Blocking findings

### HIGH — resolved selector is recorded but never verified against actual optimizer membership

`tools/g0/collect_r09_b2_optimizer_inventory.py:74-78,116-117` records both `selected_by_resolved_selector` and `selected_by_optimizer`, which is the correct data model.

But `tools/g0/verify_r09_b2_optimizer_inventory.py:14-35` only compares actual optimizer membership (`selected`) with flattened optimizer groups (`grouped`). It never reads `selected_by_resolved_selector` at all.

Therefore an artifact can have a wrong optimizer selection relative to the resolved recipe selector, while `selected_equals_groups=true`, and still satisfy `pass_ready`.

Required fix: derive the resolved-selected stable-name set from `selected_by_resolved_selector` and hard-gate it against the actual optimizer membership, with any intentionally allowed exclusion/override encoded explicitly and narrowly. Do not treat group self-consistency as proof of selector correctness.

### HIGH — recurrent-vs-TTT matched-diff / allowed-difference contract is still absent

`tools/g0/verify_r09_b2_optimizer_inventory.py:42-45` validates each backend independently and defines `pass_ready` as “all per-backend booleans are true”. There is no cross-backend comparison of trainable/selected parameter names, optimizer groups, or the frozen backend-specific allowlist.

This directly leaves open a blocker from the approved P3 plan and prior review: recurrent and `ttt_fast_weight` can each be internally valid yet differ in arbitrary persistent trainable/optimizer membership and still PASS.

Required fix: add a machine-readable `matched_diff` section and verifier hard gate. Compare the recurrent/TTT resolved selector sets and actual optimizer sets; only the explicitly frozen backend-specific difference set may differ. Any extra common-core or unexpected backend-specific difference must fail-close.

### HIGH — optimizer-state and DCP persistent-state semantics are not actually verified

`tools/g0/verify_r09_b2_optimizer_inventory.py:10-35` never validates `optimizer_state` fields, including `not_materialized`, `eligible_parameter_names`, or state entries. It also reduces DCP validation to `dcp_state.inspected is True`; `ttt_dynamic_excluded` checks only model parameters/buffers, not DCP keys/state membership.

Thus a future PASS artifact could claim `dcp_state.inspected=true` while containing forbidden TTT runtime members, or could contain inconsistent/malformed optimizer-state eligibility/materialization information, and still satisfy `pass_ready`.

Required fix:
1. hard-gate optimizer-state eligibility against actual optimizer param-group membership;
2. if `not_materialized=true`, require no materialized state entries; if false, validate every state entry reverse-maps to an eligible stable parameter name and records the expected state-key metadata;
3. when DCP is inspected, persist the inspected stable key/schema membership and explicitly prove the frozen five TTT runtime members (`W`, `pending_evidence`, `last_evidence`, `initialized`, `segment_progress`) are absent from DCP persistent state;
4. make those checks mandatory for backend/P3 PASS.
