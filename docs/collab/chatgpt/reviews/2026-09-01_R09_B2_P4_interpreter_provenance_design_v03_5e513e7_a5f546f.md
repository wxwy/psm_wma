## Scope

This is a design-only review of `docs/build/PSM-WMA_R09_B2_P4_interpreter_provenance_design_v0.3_2026-09-01.md`. No implementation, P4 record regeneration, P5 export/compose, GPU, training, evaluation, or inference is authorized.

v0.3 successfully closes the three blockers from the prior v0.2 review: the full P4 install profile now includes the `train` project extra plus `cu130` dependency group; registry/editable/VCS sources are separated; and the CPython 3.13 absent `python313.zip` candidate is explicitly modeled and removed before the P5 runtime path is constructed.

Two new trust-boundary gaps remain before implementation can be authorized.

## Findings

### HIGH — the hardened `-I -S` startup contract protects P5, but not the actual P4/D005 training interpreter startup

The design's hardened startup grammar is explicitly attached to the future P5 child: lexical venv launcher + `-I -S`, then stdlib-only provenance validation, then an exact four-entry runtime `sys.path` before Hydra/Pydantic/Cosmos imports.

However the P4 D005 command being re-frozen is still the real training entrypoint (`cosmos_framework.scripts.train` via `torch.distributed.run`). The current P4 command contract uses a normal Python startup, not `-S`. Therefore normal `site` initialization processes the venv's `.pth` files before the training module runs.

v0.3 explicitly allows `_editable_impl_cosmos_framework.pth`, `_virtualenv.pth`, `a1_coverage.pth`, and `distutils-precedence.pth`, and acknowledges that some allowed `.pth` files contain `import` statements. Binding only each `.pth` basename/raw SHA proves the startup statement bytes, but it does not independently bind the target module(s) executed by those statements or the normal-site `sys.path` they can influence.

A P4 interpreter provenance contract must cover the interpreter that will actually execute D005, not only the safer P5 inspection process. Otherwise P5 can prove a clean modeled environment while a later real D005 launch can execute additional startup code before `torch.distributed.run` under a different import graph.

Required design fix: choose and freeze one P4 runtime startup model.

1. Either harden the actual future P4/D005 Python startup as well (with a reviewed bootstrap/path construction contract equivalent in strength to the P5 path); or
2. retain normal `site` startup, but then make the P4 provenance explicitly bind normal-site behavior: exact `.pth` execution order/content, every module imported by executable `.pth` statements and its source/payload provenance, the resulting canonical P4 runtime `sys.path`, and all startup customizations. Unknown/import-dependent `.pth` behavior must fail closed.

Permanent negatives must show that changing an executable `.pth` import target or its imported payload causes P4 verification failure even when the `.pth` file itself is unchanged.

### HIGH — generated bytecode is executable import payload but is outside the proposed source truth

The source-type grammar independently binds tracked/editable source files, registry-wheel RECORD payload, and VCS source trees. It does not define the treatment of installer/runtime-generated `__pycache__/*.pyc` or other sourceless `.pyc` files under the future import roots.

Python can execute valid cached bytecode instead of recompiling the verified `.py` source. Therefore a tampered but structurally valid `.pyc` can become the executed object while the wheel/source file hashes, RECORD, Git tree, and package metadata remain unchanged. This creates a false-PASS path for both the P5 post-bootstrap imports and the later P4 runtime unless bytecode is explicitly removed from the import trust surface.

Required design fix: define a verifier-owned bytecode policy. A sufficient design is one of:

- reject every `__pycache__` / `.pyc` under all approved project/site-packages import roots before the authorized runtime; or
- force imports to a separately controlled empty pycache location and prove existing local bytecode cannot be read, while preventing bytecode writes for the static P5 path; or
- independently bind every executable bytecode artifact to a reproducible source-derived truth (more complex and not preferred).

Add permanent negatives for a modified cached `.pyc` with unchanged source bytes/metadata and for an added sourceless `.pyc` under an approved import root.

### MEDIUM — "clean" source check must explicitly mean tracked + untracked empty for every importable source root

The design uses tracked-tree digests for first-party and VCS source roots and refers to clean checkouts. Because those roots are later inserted directly into `sys.path`, an untracked `.py`, package directory, extension module, or namespace fragment can influence import resolution without changing a tracked-tree digest.

The implementation contract should state unambiguously that production framework root/submodule and every VCS checkout must pass `git status --porcelain=v1 --untracked-files=all` with empty output (plus the existing exact revision/tree checks). Add an untracked import-shadow negative test.

## Positive observations

- `project_extras=["train"]` and `dependency_groups=["cu130"]` now reflect the training entrypoint rather than a compose-only minimum.
- `pyproject.toml`/`uv.lock` are verifier-owned frozen Gitlink sources rather than caller-owned truth.
- Registry wheel, first-party editable, and Git/VCS source types now have separate provenance models.
- The editable project no longer forces an unsafe blanket `.pth` rejection; P5 still avoids executing `.pth` via `-I -S`.
- The CPython 3.13 `python313.zip` candidate is narrowly modeled as the one allowed absent bootstrap path and removed before third-party imports.
- Old P4/P5 attempts remain historical and cannot be retried.
