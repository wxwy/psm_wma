## HIGH — parent collector does not enforce the runbook's fail-stop semantics

The runbook freezes the execution rule as: any nonzero worker exit, `BLOCKED`/`FAIL`, or peak-cap violation must stop immediately and must not run another backend. The current parent collector does not implement that rule.

In `tools/g0/collect_r09_b2_p3_gpu_inventory.py` (static implementation `c9058b6`, parent orchestration loop around the backend subprocess launch), when a child returns nonzero the code only records:

```python
backends[backend] = {
    "status": "BLOCKED",
    "reason": ...,
}
```

and then continues the `for backend in ("recurrent", "ttt_fast_weight")` loop. Therefore a recurrent worker that exits because of OOM, the 24 GiB stop gate, processor/model/optimizer construction failure, or another hard failure can still be followed by launching the TTT worker. That contradicts the reviewed runbook's `立即停止，不重跑` safety boundary.

This matters specifically for run authorization: the stop condition must be machine-enforced, not only described in prose.

### Required fix

1. After the first backend child returns nonzero, persist the available failure evidence and stop orchestration without launching the remaining backend.
2. Likewise, if a child exits zero but its JSON status is not `PASS`, stop before launching another backend.
3. Preserve D005, stdout/stderr/failure reason, and any already-written backend JSON for audit; do not retry automatically.
4. Add a permanent regression that mocks/isolates child launch and proves:
   - recurrent nonzero => exactly one child launch; TTT is never launched;
   - recurrent `status=BLOCKED`/`FAIL` with zero exit => TTT is never launched;
   - only a recurrent `PASS` permits launching TTT.

The exact command, single-GPU binding, `max_peak_gib=24`, local processor exception, no VAE/data/checkpoint/forward/backward/step boundary, and the previously approved static P3 verifier/inventory contracts otherwise remain acceptable for the next review.

## Scope

No GPU execution is authorized by this review. In particular, `APPROVE_TO_RUN_GPU_ONLY_P3_GATE` is **not** granted. B2-T/P4/P5, training, evaluation, inference, closed-loop/SR, multi-GPU, long training, backend freeze, Global/Agent/RL remain outside scope.
