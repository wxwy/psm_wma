## Findings

### HIGH — P5 does not yet prove that P4-v4 evidence came from a committed full-clean evidence root

`docs/build/PSM-WMA_R09_B2_P4_v4_execution_preflight_design_v0.1_2026-09-02.md:5-15` treats closed P5 v0.9 static tooling as the authoritative future consumer and fixes the future evidence paths under `artifacts/g0/r09/b2/p4_execution_preflight_v4/...`.

However the current consumer does not establish the repository-level authority assumed by that design. `tools/g0/verify_r09_b2_p5_full_config_diff.py:148-156` only resolves `evidence_root`, checks non-overlap with `exporter_root`, then calls `load_p4_v4_preflight(root)` / `_p3_contracts(root)`. `tools/g0/export_r09_b2_p5_resolved_config.py:~280-340` reads the three fixed JSON files as regular canonical files and validates their internal/runtime bindings, but does not require `evidence_root` + submodule to be tracked+untracked full-clean and does not independently require each `request.json/result.json/verification.json` current byte stream to equal `git show HEAD:<fixed-path>`.

Concrete false-PASS class: copy otherwise valid frozen P1/P3/P4-v4 files into a mutable/non-Git directory, or mutate the P4-v4 files together while preserving their internal SHA chain and referenced production/run/staging truth. P5 has no independent Git commit identity for the three evidence files themselves.

This is also reflected by the existing permanent P5 fixture, which deliberately constructs P4-v4 evidence under a temporary non-Git directory and expects the pair verifier to pass.

Required before this preflight Gate is implemented: either remediate the P5 consumer prerequisite first, or explicitly include that prerequisite remediation in a separately reviewed scope. P5 must fixed-discover the three files from a full-clean Git evidence root, bind root revision/Gitlink/submodule, and verify Git-blob bytes == current bytes for all three files before accepting them as authoritative evidence.

### HIGH — execution output and committed/refrozen evidence lifecycle are not defined

`docs/build/PSM-WMA_R09_B2_P4_v4_execution_preflight_design_v0.1_2026-09-02.md:11-15` says the future artifacts have fixed repository paths and that a separately approved parent will materialize final `<run_root>/import_staging/<token>` and recompute manifest/native closure/roster there. It does not define how runtime-produced request/result/verification bytes move from the execution process into the committed, full-clean evidence root that P5 is supposed to consume.

These are different trust/write domains:

- `production_source_root`: read-only Git production source;
- `p4_run_root` / final `p4_staging_root`: writable exactly once by the approved execution parent, then read-only;
- candidate preflight evidence: generated by the execution tooling;
- committed `evidence_root`: Git checkout that P5 must later read as full-clean immutable evidence.

A preflight process cannot simply write authoritative JSON directly into the eventual full-clean evidence checkout and simultaneously claim that checkout is immutable committed truth.

Required: freeze a two-stage handoff. The one-shot execution writes candidate request/result/verification/failure evidence outside all Git trust roots; a separate reviewed record/refreeze step independently verifies the candidate and final run/staging state, copies only canonical PASS evidence to the fixed repository paths, commits it, and records the resulting evidence revision/SHA. P5 may consume only that committed/refrozen identity. A failed candidate must never be refrozen as PASS.

### HIGH — one-shot final-path failure and retry semantics are under-specified

`docs/build/PSM-WMA_R09_B2_P4_v4_execution_preflight_design_v0.1_2026-09-02.md:13-15` correctly requires native/ELF closure to be recomputed at the final canonical staging path. That means the approved parent must mutate the final `p4_run_root` before it knows whether the complete preflight will PASS.

The design does not state:

- `p4_run_root` freshness precondition before the one-shot attempt;
- whether `run_token` is verifier-owned and unique;
- what remains after failure midway through copy/manifest/ELF/roster construction;
- whether the same run-root/token may be cleaned, repaired, or retried;
- PASS publication point and immutable post-PASS state;
- how failure evidence is retained without becoming an allowed P5 roster entry.

Without this, an implementation can fail after partially materializing final staging, modify/repair that same final tree, and later emit a PASS for the same identity, washing out the failed provenance.

Required: fail-closed one-shot lifecycle. At minimum, final run root absent before preflight; unique verifier-owned token/attempt; first creation consumes the identity; any exception leaves immutable failure evidence and permanently invalidates that run-root/token for PASS; no cleanup-and-retry/reuse; only a completely successful single attempt may emit candidate PASS result/verification and transition the final staging tree to the exact read-only roster.

### MEDIUM — prerequisite consumer/producer contracts are named but not pinned to exact revisions

`docs/build/PSM-WMA_R09_B2_P4_v4_execution_preflight_design_v0.1_2026-09-02.md:5-7,17-19` refers to “P4 interpreter-provenance v1.3” and “P5 v0.9 static tooling” / “P5 v4 verifier grammar”, but does not bind exact root commits, review commits, tool paths, or source hashes.

Because this Gate produces evidence consumed by P5, both sides must not drift together after design approval. Freeze the exact upstream contract identities the preflight builder/verifier must satisfy (root revision + relevant tool/file SHA or exact approved design/implementation commits). Any later grammar change must require a new design/review rather than silently changing both producer and consumer.

## Positive observations

- The Gate boundary is correctly separated from actual execution: this request does not authorize staging, refreeze, compose, GPU, or training.
- Final-path recomputation of manifest/Python universe/ELF closure is the correct provenance model; relocation-based closure would be unsafe.
- Reusing the already-developed lexical `-I -S -B -c` loader, bootstrap byte binding, runtime sys.path, native-load analysis and roster grammar is directionally correct.
- The proposed CPU negative-test areas (hidden Python, ELF second-site, loader/bootstrap/environment/sys.path drift) are appropriate once the lifecycle/authority contracts above are frozen.
