## 4. HIGH-F1 — Cross-worker Core publication can race coordinator fault registration, creating an unrecoverable D1 error

**Root cause and exact source:**

1. Root scripts/robocasa_eval_v2/runtime.py:490-615 runs up to three futures. When TaskA fails, the coordinator sets stop and at 605-615 records coordinator_stop errors for **every currently active Task**, including TaskB currently committing Core. These fault calls are NOT serialized through the scheduler commit lock and do NOT wait for all in-flight Core transactions to finish.
2. Child cosmos_framework/evaluation/robocasa_v2/store.py:793-833 checks _healthy_stream at line804, then separately performs Core evidence validation, fsync and staging writes, and eventually os.replace(staging,target) at line828. There is no shared linearization fence or final health check before publication.
3. Child store.py:849-866 computes frozen core_committed_at_fault by checking _result(task, attempt.episode) at the instant of fault registration; it is False if TaskB has not yet published public Core.
4. Child store.py:895-918,929-965 allows a pre-Core attempt-scoped fault to resolve only via a valid **different attempt ID** for the same logical Episode; execution-only resolution requires frozen core_committed_at_fault True. Root runtime.py:104-126 likewise declines to auto-resolve an older fault when the eventual valid row uses the **same** attempt ID.

**Reachable interleaving — from source, not a measured GPU reproduction:**

- GPU5 TaskB enters Store.commit; healthy stream check passes; pauses after validation but immediately before os.replace.
- GPU4 TaskA fails. The coordinator catches the exception and records TaskB coordinator_stop using TaskB latest_attempt; public Core not yet present, so core_committed_at_fault=False becomes immutable.
- GPU5 TaskB resumes and atomically publishes a valid Core from that SAME attempt (commit path does not recheck new fault).
- Resume correctly skips TaskB valid Core (Owner D3/D5), but the old attempt-scoped error cannot use execution-only recovery (False flag) and cannot use valid-retry recovery (same attempt; valid Core immutable). Clean Qualification remains blocked indefinitely.

This violates D1 recoverability and D3/D5 no-retest semantics on a normal intended 3-GPU concurrent failure path. Existing200 author tests assert fault recovery and concurrent scheduler success separately, not this cross-worker ordering. Do not interpret the JUnit PASS as false; it does not cover this schedule.

**Required narrow fix / acceptance:**
- Choose one rigorous linearization policy: serialize publication and fault classification under a shared coordinator/Store gate (and enforce stop before later publication), **or** explicitly support audited same-attempt committed-after-inflight-fault recovery with positive cleanup, exact Core identity and new health receipts. No deletion/relabeling of old immutable evidence, no repeated valid Episodes.
- If fault occurs BEFORE Core publication: that stale attempt must not publish valid Core afterwards. If Core publishes BEFORE the fault: classification/recovery must treat the fault as post-Core, retain byte-identical valid result and permit execution-only remediation.
- Deterministic 3-worker CPU injection test: TaskB pauses inside Core Commit between healthy check and publication; TaskA fails and enters coordinator-wide fault registration; release B. Assert no valid same-attempt Core + permanently unresolvable pre-Core fault combination. Test reverse order (B commits before A faults), cleanup, new stream health, Resume skip, results_qualified eventually true, normal behavioral failure and success both preserved. Include source-bound fresh test evidence and true Root+Child formal SHA.
- Focused incremental Code Gate only on F1; do not re-audit or rerun unchanged approved design implementation merely to inflate test counts.

**Severity:** HIGH. This is a code-level concurrency reachability finding; no direct real-GPU reproduction was performed.
