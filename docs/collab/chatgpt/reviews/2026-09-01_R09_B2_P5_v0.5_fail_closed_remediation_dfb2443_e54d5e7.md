## Findings

### HIGH — actual exporter/verifier execution identity is not bound to `exporter_root`

`tools/g0/export_r09_b2_p5_resolved_config.py:210-236`

The remediation correctly makes `verify_pair()` recompute the expected exporter revision/tool SHA from the supplied clean `exporter_root`, but the parent path does not require the code it actually executes to come from that root.

`run_parent_export()` launches the child with `Path(__file__).resolve()` and imports `tools.g0.verify_r09_b2_p5_full_config_diff` from the current Python import path. Meanwhile, `exporter_root_revision` and `tool_sha256` are caller-supplied values written into the envelope. Therefore code can execute from checkout A while provenance is validated against clean checkout B. If A is unreviewed/dirty and B is the approved exporter root, the actual executed child and imported pair verifier are not the code being attested.

Required before requesting static export:

- bind the currently executing exporter file to exactly `<exporter_root>/tools/g0/export_r09_b2_p5_resolved_config.py` (canonical path + SHA);
- bind the verifier implementation actually invoked/imported to exactly `<exporter_root>/tools/g0/verify_r09_b2_p5_full_config_diff.py`;
- preferably derive `exporter_source` internally from `exporter_root` and remove caller ownership of `tool_sha256` / `exporter_root_revision`;
- launch the child from the exporter-root-owned script path, not an unconstrained `__file__`;
- add a CPU negative where execution/import comes from checkout A while `exporter_root` points to clean checkout B; this must fail before any child compose.

This is a trust-boundary issue: the verifier currently proves the identity of B, not necessarily the identity of the code that produced or verified the artifacts.

### MEDIUM — failed staging attempts are retained but not marked FAIL

`tools/g0/export_r09_b2_p5_resolved_config.py:210-236`

The v0.4 contract requires a failed `attempt-<uuid>` to remain as separate evidence and be explicitly marked `FAIL`. The current function creates the attempt directory and relies on exceptions from child execution / pair verification, but there is no `try/except/finally` path that writes a failure record. A failed attempt can therefore remain as an ambiguous partial directory.

Required:

- after staging begins, catch child / parsing / pair-verifier failures;
- write a deterministic fail-closed status record in that attempt directory;
- never create/rename the canonical result root on failure;
- add a CPU fixture for a forced child/verifier failure proving the attempt remains separately marked FAIL and canonical output is absent.

## What is now correct

The four findings from the previous review were materially remediated:

- production/evidence/exporter roots are canonicalized and parent-side three-root overlap is rejected;
- production root and its submodule are tracked-clean and the absolute D005 root is frozen;
- D005 cwd, PYTHONPATH, stream-manifest env path, and stream-manifest asset path/realpath are contained under the frozen production root;
- evidence P4 recurrent/TTT/verification files are bound to frozen closed SHA256 constants and PASS schema/status;
- parent-supplied D005 records must equal the frozen evidence-root records;
- evidence and exporter roots are independently clean-bound;
- nested verifier-owned envelope objects now enforce exact key sets;
- P4 record-file SHA is separated from the record's internal `d005_sha256`;
- CPU fixtures cover root relocation, equal/symlink roots, dirty production, immutable P4 identity, nested unknown fields, and child pre-compose bootstrap.
