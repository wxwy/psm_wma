## Findings

No blocking findings within the requested P3-only scope.

The v0.3 contract now matches the already-closed P4 record shape:

- recurrent and TTT must bind the same P3 inventory path and exact artifact SHA;
- common P3/P4/P1 production provenance and PASS-evidence identity must remain equal across both envelopes;
- only `backend_contract.selector_keys` and `backend_contract.optimizer_membership_sha256` may differ at the P3-binding layer;
- each backend-specific value must be independently recomputed from the shared P3 artifact plus verifier-owned recurrent/TTT selector rules, rather than accepted merely because the two records differ;
- missing/extra backend-contract fields, swapped recurrent/TTT contracts, arbitrary selector values, or any P3 path/SHA/PASS-identity drift must fail closed;
- actual parameter/optimizer membership remains evidenced by P3 and is not invented as a synthetic P5 resolved-config field.

This resolves the prior contradiction that simultaneously allowed backend-specific P3 contracts while requiring the whole P3 binding to be identical.

## Required implementation coverage

The permanent CPU fixtures must preserve the design's actual-P4-shape cases:

1. same P3 path/SHA and correct distinct recurrent/TTT backend contracts => PASS;
2. path or SHA drift on either side => FAIL;
3. recurrent using the TTT contract, TTT using the recurrent contract, or either using an arbitrary contract => FAIL;
4. missing or extra backend-contract fields => FAIL;
5. any resolved selector/config-membership difference not directly mapped to the verifier-owned backend contract => FAIL.
