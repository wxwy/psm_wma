## Why this plan is acceptable

The plan correctly treats P3 as a read-only inventory gate rather than a training gate. It explicitly separates recipe selectors from actual model parameters, optimizer param-groups, materialized optimizer state, and DCP serialization membership. It also fail-closes if an actual full-recipe construction cannot be obtained under CPU/meta-safe, no-weight/no-checkpoint/no-forward/no-step constraints, and forbids replacing that failure with a synthetic PASS.

The plan also correctly requires reverse mapping every optimizer parameter object to a unique model named parameter and requires the frozen B0 TTT runtime state (`W`, `pending_evidence`, `last_evidence`, `initialized`, `segment_progress`) to remain outside persistent model/optimizer/DCP parameter state.

## Implementation hard gates

1. **Inventory scope must be exact and explicit.** `model_parameters` must include every parameter relevant to the actual resolved optimizer selection, not only names containing `Local`; additionally emit a separate Local/backend subset if useful. Do not let a narrow reporting filter hide unexpected common-core trainable parameters.
2. **Distinguish three optimizer facts:**
   - optimizer param-group membership;
   - current materialized optimizer-state membership;
   - state eligibility implied by param-group membership.
   If Adam state is empty before the first step, record `not_materialized=true`; do not infer or fabricate `exp_avg`/`exp_avg_sq` tensors.
3. **Object identity is an in-process proof only.** Use Python object identity to build the reverse map, but persist stable parameter names/counts/metadata in the artifact; do not treat raw `id()` values as cross-run provenance.
4. **DCP inspection must remain read-only.** If obtaining DCP keys requires checkpoint save, device materialization, weight load, optimizer step, or other state mutation, return `BLOCKED` for that portion rather than weakening the contract.
5. **Matched-diff must expose real selector consequences.** If recurrent and TTT actual trainable/optimizer sets differ outside the documented backend-specific allowance, the artifact must be `FAIL`/`BLOCKED`; do not normalize away differences merely because they originate from different recipe selectors.
6. **Provenance must bind the construction path.** Record root/submodule/Gitlink, recipe SHA, collector/verifier SHA, resolved selector environment, construction mode (`cpu`/`meta`), and the source SHA(s) of the parameter-selection/optimizer-construction code actually used.
7. **No hidden materialization.** Hard-gate `weights_loaded=false`, `checkpoint_loaded=false`, `forward_executed=false`, `backward_executed=false`, `optimizer_step_executed=false`, `scheduler_step_executed=false`, and no CUDA initialization/device use attributable to P3.

## Authorized scope

Approval authorizes only P3 collector/verifier implementation, CPU/meta-safe targeted tests, and the P3 artifact. It does **not** authorize checkpoint/model-weight/VAE/tokenizer/data loading, GPU, forward/backward, optimizer or scheduler step, training, B2-T, P4/P5, evaluation/inference/closed-loop, SR, or backend freeze.

P3 closure requires a new implementation/evidence SHA and independent review.
