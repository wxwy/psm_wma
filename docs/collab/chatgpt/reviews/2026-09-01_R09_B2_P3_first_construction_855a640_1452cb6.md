## Verdict

**REQUEST_CHANGES**

The previous first-construction ordering blocker is substantially closed. The submodule now extracts the actual production primitive `build_vlm_processor(vlm_config) -> lazy_instantiate(vlm_config.tokenizer)`, and `OmniMoTModel.set_up_tokenizers()` uses that same helper. P3 no longer needs an already-constructed `OmniMoTModel` or a second `set_up_tokenizers()` call.

However one HIGH binding gap remains.

## HIGH — precondition validates one tokenizer config, but construction can consume a different `vlm_config.tokenizer`

`prepare_isolated_worker(edge_checkpoint_path, tokenizer_config)` validates and records a standalone `tokenizer_config` dict in `record["resolved_tokenizer_binding"]`.

Later, `run_production_processor_construction(record, vlm_config)` directly calls:

`build_vlm_processor(vlm_config)`

There is no check that the exact `vlm_config.tokenizer` consumed by `build_vlm_processor` is identical to the binding validated during `prepare_isolated_worker`.

The construction witness then hashes `record["resolved_tokenizer_binding"]`, not the actual tokenizer config consumed by `build_vlm_processor`.

Therefore this sequence is still possible:

1. prepare/validate a safe local binding A;
2. pass a different production `vlm_config` containing binding B to construction;
3. construct from B;
4. witness still reports SHA256(A) and can satisfy the verifier.

This breaks the required chain `validated binding == actual production construction input`.

## Required fix

Before construction, derive a canonical machine-readable binding from the **actual `vlm_config.tokenizer` object that will be passed to `build_vlm_processor`**, at minimum:

- `repository`
- `revision`
- `tokenizer_type`

Then require exact equality with `record["resolved_tokenizer_binding"]` before calling `build_vlm_processor`.

Preferably remove the two-source API entirely: `prepare_isolated_worker` should receive the resolved production `vlm_config` (or its exact tokenizer object), extract/validate the binding itself, and the same object/immutable snapshot should flow into construction.

The construction witness `binding_sha256` must be computed from the canonicalized **actual construction input**, not copied/recomputed only from the prior record.

Add permanent negative regressions:

- prepare with valid local binding A, construct with remote binding B -> fail before constructor invocation;
- prepare with valid local binding A, construct with different local path B -> fail before constructor invocation;
- mismatched construction binding must not be able to produce a PASS artifact even if phase trace/after snapshot/constructor identity are otherwise valid.

A static unit test may mock `build_vlm_processor` and assert it was **not called** on binding mismatch; no processor construction is required for this review round.
