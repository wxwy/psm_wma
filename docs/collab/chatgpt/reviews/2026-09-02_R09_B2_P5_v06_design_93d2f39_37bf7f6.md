## Scope

Design-only review. I independently reviewed the v0.6 migration from the old P4-v2/fixed-request P5 identity to the proposed P4-v4 execution-preflight identity, together with the inherited v0.2-v0.5 P5 contracts and the currently approved P4 interpreter-provenance design/tooling. No P4 preflight, staging, P5 compose/export, torchrun, CUDA/GPU, model/data access, training, evaluation, or inference is authorized by this review.

## Findings

### HIGH — `production_root` conflates the Git source root and the run-local final staging root

`docs/build/PSM-WMA_R09_B2_P5_full_config_diff_design_v0.6_2026-09-01.md:11-17` requires a completed P4 final-path copy-only staging, then defines `production_root` as the preflight's “final canonical staging/source root” while also requiring all three roots to satisfy `git status --porcelain=v1 --untracked-files=all` clean.

That is incompatible with the already approved P4 contract. `docs/build/PSM-WMA_R09_B2_P4_interpreter_provenance_design_v1.0_2026-09-01.md:7-9` places the final P4 import staging under `<D005 run_root>/import_staging/<run-token>`, created by the future execution parent. The frozen P4 evidence also demonstrates that the source worktree and run root are different trees: the source cwd is `/disk/rl/psm_wma_p4_d005_retry/cosmos-framework`, while recurrent `outputs.run_root` is under `/disk/rl/data/psm_wma_p4_d005_outputs/recurrent/...` (`artifacts/g0/r09/b2/p4_launch_d005/recurrent.json`). The run-local staging therefore cannot simultaneously be the Git production checkout whose cleanliness/revision/Gitlink are verified.

This ambiguity is security-relevant: an implementation can choose the Git checkout and silently lose the final `$ORIGIN`/staging binding, or choose the staging directory and lose the Git source identity/full-clean check.

Required revision:

- define separate canonical identities for `production_source_root`, `p4_run_root`, and `p4_staging_root`;
- apply Git HEAD/Gitlink/full-clean to `production_source_root`, `evidence_root`, and `exporter_root`, not to the non-Git staging tree;
- independently bind `p4_staging_root` to the approved preflight, exact copy-only manifest, native closure, readonly state, and non-overlap/symlink rules;
- state exactly which root supplies child cwd/TOML and which paths form runtime `sys.path`. Under the P4 `-I -S -B` contract, production `PYTHONPATH` cannot be treated as import authority; runtime imports must remain bound to the verified staging plus the approved base stdlib/lib-dynload;
- add permanent negatives for source/staging substitution, relocation, symlink alias, and a same-byte ELF staged at a different `$ORIGIN` path.

### HIGH — the authoritative P4-v4 execution-preflight evidence contract is not defined

`...P5_full_config_diff_design_v0.6...md:11`, `:17`, and `:31` make P5 depend on an independently approved P4 execution preflight and require the P5 verifier to independently recompute the P4 request/defaults and preflight identity. But v0.6 does not define the authoritative preflight artifact schema, file identity, storage location, verification status, or producer/verifier provenance from which that identity is obtained.

The currently approved static P4 implementation does not fill this gap. `tools/g0/verify_r09_b2_p4_d005.py::_template_ok` freezes a static `interpreter_provenance_template` (bootstrap identity, request defaults/schema keys, payload manifest, agent/worker argv templates); it is not an execution-preflight result schema containing the actual final `run_root/staging_root`, request digest, materialized manifest/ELF closure/native TCB, preflight status, or verification artifact. Meanwhile the committed P4 evidence in `artifacts/g0/r09/b2/p4_launch_d005/` is still the historical v2 evidence.

v0.6 additionally says each P5 request carries “P4 record/verification file SHA” without specifying whether that means the historical v2 files, a new v4 static record, or future preflight files. P5 static tooling cannot safely implement this by guessing.

Required revision:

- explicitly decide whether a new P4-v4 record/refreeze is a prerequisite; historical v2 evidence must not silently satisfy a v4 execution-preflight identity;
- freeze the exact per-backend P4 preflight request/result/verification schema and exact top-level/nested key sets;
- bind at minimum: source root/revision/Gitlink, run root, final staging root, request SHA, request defaults, lexical interpreter/loader argv, effective/native-loader environment, payload/staging manifest SHA, ELF/native closure identity, status, producer/verifier tool identity, and verification SHA;
- define where these files live and how P5 discovers them without a caller-supplied path becoming truth;
- require the P5 verifier to independently re-hash/re-derive the current staged/preflight state before trusting the recorded PASS;
- add a shared-forgery negative where caller request and supplied preflight artifact are mutated consistently and must still FAIL.

### HIGH — the P5 pre-spawn environment grammar is underspecified relative to the P4 native-loader trust boundary

`...P5_full_config_diff_design_v0.6...md:17` requires an “exact effective environment”, but does not define how the P5 mode projects the P4 preflight environment into the child process. This matters before Python executes: P4 v0.8 explicitly requires the native-loader environment to be constructed under the same sanitized profile used for dependency resolution/spawn, with loader injection/search variables absent. P4 torchrun workers additionally have verifier-owned rank/world variables; a P5 static child is not a torchrun worker and must not inherit those keys.

Required revision:

- define a verifier-owned `p5_effective_environment` grammar constructed from an empty environment;
- explicitly preserve only the production/P4 common `set` values and the backend-specific values that P5 is intended to compare;
- require `RANK`, `WORLD_SIZE`, `LOCAL_RANK`, `MASTER_ADDR`, `MASTER_PORT` absent for P5 compose;
- require `LD_PRELOAD`, `LD_AUDIT`, `LD_LIBRARY_PATH`, the rest of the approved P4 loader-variable set, and `GLIBC_TUNABLES` absent before child spawn;
- freeze locale/startup additions explicitly rather than inheriting ambient parent state;
- require the parent and pair verifier to independently reconstruct the same environment and the child to assert exact equality after startup;
- add permanent negatives for ambient `LD_PRELOAD`/`LD_LIBRARY_PATH`, rank-variable leakage, unknown inherited variables, and locale drift.

### MEDIUM — preflight-created `run_root` needs an exact pre-training contents contract

The proposed P4 preflight necessarily changes the old `fresh` state from “run root absent” to “run root exists and contains preflight staging”. Before P5 uses that identity, it must be possible to prove that no training/partial-execution artifacts already exist. The v0.6 stop-condition prose mentions checkpoint/model/data I/O but does not freeze an allowed run-root roster.

Required revision: define the exact post-preflight/pre-P5 allowed contents (for example the approved staging/preflight evidence only), and fail if checkpoint directories, stdout/capture/training artifacts, unknown files, or extra staging trees are present. Fold this roster into the verifier-owned preflight identity and add a partial-training-artifact negative.

## Positive observations

The direction of the v0.6 migration is otherwise sound and should be retained:

- old P5 attempts/request SHA/output roots remain permanently non-retryable;
- the P5 child uses the verified lexical `-I -S -B -c` loader with an out-of-band request SHA and Git/current-byte bootstrap binding;
- direct exporter-script and `-m` launch shapes are explicitly forbidden;
- fresh child processes, attempt preservation/canonical absence on failure, and atomic promotion after pair PASS remain appropriate;
- the v0.2 canonical full-tree grammar and v0.3 exact P3 common-evidence/backend-contract split remain the correct basis for the resolved-config comparison;
- execution authorization remains correctly separated from static-tool implementation authorization.

## Gate decision

**REQUEST_CHANGES**.

`APPROVE_TO_IMPLEMENT_P5_V06_STATIC_TOOLS` is **not granted**.

A revised design should keep the verified-loader/request-SHA/three-Git-root/attempt/full-envelope/P3-diff structure, but must first make the P4-v4 handoff mechanically unambiguous: split source vs run/staging identities, freeze the authoritative preflight evidence schema, and freeze the P5-mode pre-spawn environment and run-root roster.

Still unauthorized:

- P5 exporter/verifier v0.6 implementation under this design;
- creation/execution of a P4 execution preflight or final staging;
- P4 record regeneration/refreeze;
- P5 export/retry/compose or `load_experiment_from_toml`;
- torchrun/distributed execution;
- CUDA/GPU;
- model/dataloader/optimizer/checkpoint construction;
- weights/data/MP4 access;
- training/evaluation/inference;
- P5 closure;
- B2-T, Local Memory training, or any later gate.
