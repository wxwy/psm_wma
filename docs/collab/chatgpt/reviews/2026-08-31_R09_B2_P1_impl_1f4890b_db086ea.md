## What is acceptable

1. The implementation correctly moves away from seed-only identity and materializes an ordered manifest with `ordinal`, `epoch`, optimizer-update/microbatch arithmetic, suite, task/window identity and flat index.
2. The correction that cross-epoch window reuse is baseline semantics is reasonable; recording `epoch` rather than rejecting all repeated windows is the right direction.
3. The verifier now checks flat-index ↔ `(task_index, episode_index, start_frame)` reconstruction and per-record exact-window cache presence.
4. The manifest-aware dataset is fail-closed for nonzero DataLoader workers and checks scalar task/episode/start-frame identity.

## Blocking findings

### HIGH-1 — tracked evidence provenance is stale and does not describe the reviewed implementation

`artifacts/g0/r09/b2/p1_tiny_manifest_contract.json` still records:

- root `b71cfce`
- submodule `13c854c`

but the reviewed implementation root is `1f4890b` and the tracked Gitlink/submodule is `db086ea`. Therefore the current PASS/PARTIAL-PASS evidence cannot close P1 for the code now being reviewed.

**Required:** regenerate the formal P1 CPU evidence from one clean implementation root and bind exact root/submodule/Gitlink plus builder/verifier/wrapper hashes. Evidence created before later code/Gitlink changes is historical only.

### HIGH-2 — global manifest is not safely bound to the per-suite dataset consumer

The root builder emits one **global** JSONL that round-robins suites. The submodule getter accepts only `stream_manifest_path`, loads every record, and constructs `B2ManifestAwareIterableDataset(sft, records)` without a suite argument or suite filtering. The wrapper validates only `task_index`, `episode_index`, and `start_frame`; it never checks `record["suite"]` against the dataset being wrapped.

This does not implement the design contract that each suite consumer accepts only its own manifest slice. Passing the global manifest to each suite loader is invalid; passing a wrong-suite slice can also fail late or, in the worst case, silently consume a coincidentally matching local identity.

**Required:** make suite binding explicit and fail-closed. Either generate/derive per-suite ordered slices with an immutable link back to global ordinals, or pass an expected suite into the wrapper/getter and reject every record whose `suite` differs. Add negative tests for wrong-suite records and prove global observed order can be reconstructed exactly.

### HIGH-3 — required source/data provenance from the approved design is incomplete

The approved P1 design required the header to bind raw dataset `info.json` / parquet-index SHA256 and recipe TOML SHA256. The current builder header binds cache manifests and Python source hashes, but does not bind those raw-data/index or recipe hashes.

**Required:** add exact raw dataset/index and recipe TOML provenance (per suite where applicable), and hard-gate them in the verifier. A source SHA change must make the verifier fail even if records are rehashed.

### HIGH-4 — CPU replay evidence is not yet the required end-to-end manifest-aware replay

The tracked artifact reports only one `real_dataset_replay` record plus wrapper pytest text. The approved contract requires a no-model CPU replay in which requested vs observed count, ordinals and identities match for the manifest sequence. The current artifact does not machine-prove full requested→consumer→observed equality even for the tiny manifest.

**Required:** produce machine-readable requested and observed records (or hashes plus per-record comparator output) for the full tiny replay through the real dataset getter/wrapper path. Require exact count/order/ordinal/suite/task/episode/start-frame/flat-index equality. Include fail-closed tests for missing/extra/reordered observed records.

## Medium findings

1. `verify_r09_b2_stream_manifest.py` treats `--cache-root` and `--libero-root` as optional. For formal P1 closure these checks must be mandatory; otherwise `cache_window_per_record` / `flat_index_bijective` can remain trivially true without running the audit.
2. `source_complete` checks only key presence, not root/submodule/Gitlink equality to the implementation under verification. Formal verifier should receive expected revisions (or derive them from a clean root) and hard-gate exact equality.
3. Negative evidence is currently summarized as strings in the hand-authored contract. For closure, negative tests should be reproducible machine outputs tied to the same tool hashes/revisions.
